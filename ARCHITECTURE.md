# Проект 53 — DNS-мессенджер: архитектура первой версии

Дата: 28.09.2026; авторизация обновлена по решению пользователя 30.09.2026. Статус: проектное решение, не готовая реализация и не результат испытаний приложения. Реализованный wire описан в `docs/protocol.md`, текущие результаты и план — в `docs/goals/2026-09-29-client-track.md`.
Кодовое имя проекта: `53`. Рабочее имя протокола: `dmsg` (схема `dmsg://`). Имя протокола можно заменить до первого публичного релиза.

## 1. Решение и границы

Сохраняем C-транспорт из `0FL01/slipstream`, ветка `feat/rust-parity-ab`. Сервер мессенджера и общее ядро клиента пишем на Rust. Android-оболочка: Kotlin + Jetpack Compose, интеграция с Rust через UniFFI. Не переписываем DNS/QUIC, congestion control и scheduler ради единого языка.

Рабочее развёртывание существующего интернет-туннеля не меняем. Мессенджер получает отдельное развёртывание, поддомен и, для первого запуска, отдельный публичный IP/сервер. Один новый поддомен сам по себе не позволяет двум процессам одновременно занять один `IP:53/UDP`.

Версия 1: один authoritative DNS endpoint, один профиль сервера в приложении, один активный аппарат на учётную запись, личные диалоги. Пилотный предел: 16 одновременно подключённых устройств. Это проектный предел, не подтверждённая нагрузочная характеристика.

Не делаем федерацию, HA, группы, мультиустройство, видео, ботов, каналы, публичный каталог пользователей, веб-клиент или общий интернет-прокси. Не добавляем Kubernetes, Redis, PostgreSQL и объектное хранилище без измеренной необходимости.

## 2. Что подтверждено в исходной ветке

Два последних коммита на момент проверки датированы 27.09.2026:

1. `feat: port Rust runtime parity with measured transport benefit`.
2. `fix: preserve production bind and reset seed compatibility`.

В `bench/RESULTS.md` записан прирост paired-median download +21,96% против C0 в шести транспортных парах, 6/6 побед. В сценарии FlowRelay/WARP проверка регрессии loaded upload p95 не пройдена: +24,26%. Это измерения Linux/DE, не Android/LTE. Показатель loaded upload p95 нельзя выдавать за RTT или задержку звука.

Важны также изменения bounded receive credit и сохранение explicit bind/reset seed. Из отчёта нельзя выводить общее снижение расхода батареи: quiet-open polling около 19,93 запросов/с, settled-empty около 0,60 запросов/с. Постоянно открытый чат относится не к тому же состоянию, что отсутствие потоков. [S1]

Исходная сборка остаётся C/C++ с Meson/CMake, picoquic/picotls/OpenSSL. Это не готовая Rust-библиотека. Native client после разрыва установленного транспорта завершает работу; переподключение и безопасное восстановление сообщений должны находиться выше. Runtime использует глобальное состояние и обработчики сигналов. [S2, S3]

## 3. Схема

```text
Телефон A                                      Телефон B
Kotlin UI                                      Kotlin UI
    | UniFFI                                       | UniFFI
Rust core: identity, E2E, outbox, media          Rust core
    |                                              |
C Slipstream client                            C Slipstream client
    |                                              |
доступный DNS resolver                          DNS resolver
    | DNS                                          | DNS
    +-------------------+--------------------------+
                        |
              C slipstream-server
                        | private TCP, fixed destination
                     Rust msgd
                        |
                  SQLite + blobs
```

Всё, включая регистрацию, справочник ключей, файлы и сигнализацию звонков, проходит через DNS-транспорт. Не требуется доступ телефона к HTTPS API, STUN/TURN, ACME, FCM или CDN. Наличие какого-либо DNS-резолва не гарантирует прохождение туннеля: проверяется именно рекурсивный путь к выделенному поддомену.

Authoritative endpoint и recursive resolver — разные роли. В v1 один authoritative сервер; адрес доступного резолвера выбирается из профиля/сети и проверяется. UDP/TCP до резолвера определяются рабочим путём, а не названием транспорта. Python-adapter из benchmark не включается в APK; при необходимости TCP-DNS его ограниченные очереди и проверка ответов переносятся в небольшой Rust-адаптер. Число benchmark workers не переносится на телефон вслепую.

## 4. Сервер

Docker Compose содержит два сервиса: `slipstream` и `msgd`. Первый собирается из выбранной Git-ревизии и пересылает только на фиксированный backend второго. Не включаем SOCKS/FlowRelay/WARP в обязательный путь мессенджера.

Для простого loopback target сервисы могут использовать общий network namespace: `msgd` разделяет namespace `slipstream`, backend слушает `127.0.0.1:7000`, а Slipstream всегда подключается к этому адресу. Наружу у сервиса `slipstream` публикуется только `${DNS_BIND_IP}:53:5353/udp`; процесс внутри слушает непривилегированный порт 5353. Оба контейнера пересоздаются вместе как единица развёртывания. Это устраняет зависимость фиксированного target от меняющегося IP контейнера.

Администрирование: `msgctl` через локальный Unix socket внутри сервера. Операции: выдача публичного кода подключения, выбор режима регистрации, выпуск/отзыв приглашений, блокировка и перепривязка устройства, квоты, диагностика, согласованное резервное копирование. Публичной веб-админки нет. Выдача кода и переключение регистрации — планируемые дополнения, не существующие CLI-команды.

`msgd` — один Rust-процесс на Tokio. Модули: регистрация и авторизация; контакты и prekeys; очередь сообщений; передача blobs; relay и сигнализация звонков; обслуживание TTL и квот. Кодек на сервере не работает: сервер не расшифровывает, не транскодирует и не микширует аудио.

SQLite хранит users, devices, invites, contact permissions, prekeys, mailbox events, blob metadata и миграции. Новый account-auth добавит уникальный в пределах сервера логин, хеш пароля Argon2id и сохранённый режим регистрации; plaintext-паролей в БД нет. Файлы шифротекста лежат отдельно на persistent volume. Для обещания «сервер принял» используем WAL + `synchronous=FULL`, транзакции и ACK после commit; FULL не защищает от уничтожения единственного диска. В режиме WAL + NORMAL подтверждённая транзакция может быть потеряна после сбоя ОС/питания. [S4]

Native transport в прочитанном коде ограничивает число соединений максимумом 32. Пилот на 16 устройств оставляет резерв, но не решает проблему исчерпания соединений неавторизованными клиентами. Квоты по устройству действуют после авторизации; исходный адрес на authoritative сервере может принадлежать общему резолверу, поэтому агрессивный per-IP ban способен отключить всех его клиентов. [S5]

Секреты подключаются файлами read-only, не в Docker image, Git, URL логов или argv. Данные вынесены в volumes. Non-root, ограничение памяти/процессов, закрытый backend, bounded handshake и frame sizes, агрегированные метрики. После рестарта сохраняются сертификат, ключи сервера, reset seed, база и blobs.

## 5. Android и Rust

Rust core содержит протокол, криптографию, локальное хранилище, reconnect, outbox, файловые передачи, приоритеты и управление звонками. Kotlin отвечает за интерфейс, lifecycle, foreground service, разрешения, уведомления, Telecom, аудиоустройства, камеру и Keystore. UniFFI используется для команд и событий, не для отдельных PCM samples. UniFFI поддерживает Kotlin, но сам не заменяет сборку native-библиотек под Android. [S6]

`rust-mobile` используем как набор инструментов мобильной сборки и интеграции, не как обещание готового Telegram-подобного UI. Не добавляем WebView, JavaScript runtime или собственный движок виджетов.

C-клиент собирается в native library. Минимальный embedding adapter предоставляет управляемые start/stop/status и не устанавливает процессные SIGINT/SIGTERM handlers. Переподключением владеет Rust. Доступ к C runtime сериализован, одновременно работает один экземпляр. Loopback endpoint не публикуется на LAN; каждый прикладной поток проходит собственную аутентификацию. Маленький платформенный diff допускается в отдельной ветке, алгоритмы транспорта остаются прежними. Нулевой diff и управляемый Android lifecycle текущий CLI одновременно не дают. [S3]

Первый ABI: arm64-v8a; x86_64 только для тестов. Стартовый minSdk: 26, далее подтверждается на целевых аппаратах. Нужны release/LTO/strip/R8 и проверка всех native dependencies на 16 KB page sizes. Цели для профилирования: release APK до 25 MiB, idle PSS до 100 MiB на выбранном тестовом устройстве. Это бюджеты, не обещанные результаты. [S7]

Интерфейс: список диалогов, чат с пузырями и понятными статусами, запись/прослушивание голоса, карточка передачи, экран звонка, добавление контакта/QR, профиль соединения. Без стикеров, stories, typing, link previews, публичного last-seen и автоматической загрузки файлов.

APK не требует Google Play Services. QR scanner работает офлайн. На звонках нужны audio focus, маршрутизация динамик/гарнитура/Bluetooth, echo cancellation, proximity handling и корректный microphone lifecycle. Аудио-интеграция проверяется на аппаратах; язык ядра её автоматически не решает.

### Фоновая связь

Два режима: «На связи» и «Экономия». Первый явно включается пользователем, показывает постоянное уведомление и требует корректного foreground-service сценария, разрешений и, где необходимо, исключения из оптимизации батареи. Второй не обещает мгновенных входящих звонков, восстанавливает сообщения при следующем соединении.

Foreground service сам по себе не отменяет Doze. Для постоянного DNS-only соединения оценивается подходящий service type, в том числе документированный specialUse, а не бессрочный dataSync. Активный вызов использует требования phoneCall/microphone и Telecom. Подтверждение приёма звонка не должно самовольно запускать микрофон из запрещённого background состояния. Поведение force-stop и OEM battery killers не маскируется обещанием гарантированных входящих. [S8, S9]

## 6. Подключение, аккаунт и идентификаторы

### Пользовательский сценарий: код/QR → логин и пароль

На первом экране только «Вставить код подключения» и «Сканировать QR». Это один готовый публичный профиль сервера, полученный из доверенного источника: версия, tunnel domain, полный pinned carrier certificate DER и публичный Noise-ключ msgd. Он не содержит пароль, приватные ключи, приглашение или общий секрет доступа; сам по себе не создаёт аккаунт и не авторизует устройство. QR и вставленный код несут одинаковые данные. Формат нового профиля предстоит реализовать с bounded parser и версионированием; текущий wire — в `docs/protocol.md`.

Сертификат нужен целиком: `slipstream_pin.c` сравнивает DER, не только SPKI. Один домен или один публичный ключ не заменяют полный доверенный профиль. Ключ доверия не скачивается с непроверенного URL, HTTPS-shortener не нужен. Технические поля, fingerprint и ручной выбор резолвера находятся в дополнительных настройках; обычному пользователю не требуется переписывать ключи. Резолвер берётся из текущей сети. Неверный профиль отклоняется до передачи учётных данных. [S10]

После подключения к проверенному серверу доступны «Войти» и «Создать аккаунт»:

- **Войти:** логин + пароль.
- **Создать аккаунт:** логин + пароль; действующее одноразовое приглашение дополнительно требуется только в режиме `invite_only`.
- После успешной привязки устройство запоминается. Обычный запуск открывает диалоги, reconnect авторизуется сохранённым device key без повторного ввода пароля. Пароль не хранится для каждого poll и не превращается в E2E-ключ.

На сервере ровно два режима регистрации: `open` и `invite_only` (по умолчанию). Режим хранится на сервере и меняется через `msgctl`; проверка выполняется сервером, не только скрытием кнопки в UI. Он ограничивает создание новых аккаунтов, но не вход существующих. Отдельные общий access key, веб-админка и внешний сервис авторизации не добавляются.

Логин уникален в пределах сервера; это идентификатор входа, не публичный каталог и не криптографическое удостоверение. Пароль проверяется по хешу Argon2id, попытки входа и регистрации ограничены. Все account-auth операции проходят через DNS, внутри завершённого pinned QUIC/TLS + Noise handshake. До авторизации доступны только bounded операции подключения/регистрации/входа, не сообщения. Регистрация и привязка устройства атомарны и идемпотентны при потере ответа; в режиме `invite_only` сохраняются одноразовость, TTL и revocation приглашений.

### Единая новая схема и замена устройства

По новой инструкции пользователя обратная совместимость отменена: ENROL/token-replay, перенос старых аккаунтов и credential-attach не реализуются. Единый новый wire/schema для login/signup/device-key resume; старые версии отклоняются без автоматического wipe или создания новой identity. Remote-БД будет очищена отдельным последующим шагом; текущая coding-итерация не стирает remote данные и основной Android package.

Публичный контактный ID: 12 случайных символов Crockford Base32, например `7K3M-P9TX-4V2N`, с UNIQUE-проверкой на сервере. Внутренний user_id — случайные 128 бит. Человеческий ID уникален в пределах одного сервера и не является паролем или криптографическим удостоверением.

Добавление по ID создаёт ограниченный запрос на контакт. До согласия нельзя отправлять файлы и звонить. Contact QR содержит профиль/сервер, ID и полный публичный E2E identity key. При добавлении только по ID контакт остаётся непроверенным; доверенный QR или SAS закрепляет ключ. Неожиданная смена identity требует явного подтверждения.

Вход после потери телефона/переустановки возвращает доступ к новому аккаунту, не старую историю. После проверки логина/пароля требуется явное подтверждение «Заменить прежнее устройство? Оно потеряет доступ. Старая история на новом устройстве недоступна». Только затем атомарно отзываются старое устройство и его доступ, новое получает свежие локальные Noise/Olm keys при прежних `user_id`/контактном ID. CAS проверяет именно подтверждённое старое устройство. Отказ от подтверждения ничего не меняет. Одновременно активен только один аппарат; контакты видят смену E2E identity и подтверждают её явно, сообщения до confirm не теряются. Административного invite-rebind/password-bypass пути нет.

Same-install локальная копия восстанавливается только с исходным Keystore key. После Clear data/uninstall пароль или sealed-копия без этого ключа не возвращают прежние E2E keys и историю. Полноценный перенос истории, key export и multi-device не входят в v1. Отзыв устройства закрывает существующие control/media/blob sessions, а не только будущие входы.

## 7. Шифрование

Первый слой — существующий QUIC/TLS с certificate pinning. Второй — Noise IK через snow для независимой авторизации устройства и защищённого канала до msgd. На каждом независимом ordered stream свой Noise TransportState, общий счётчик между параллельными потоками не делим. Регистрацию и другие необратимые действия выполняем только после завершённого handshake, не в replayable early data. [S11]

Третий слой — E2E между телефонами. Для личных сообщений используем Olm из vodozemac без всего Matrix SDK. Приложение обязано реализовать проверку подписанных prekeys/identity bindings, атомарную выдачу one-time keys, пополнение запаса и фиксацию ключей контактов. Наличие библиотеки не означает аудит всего приложения. Состояние ratchet и ciphertext outbox фиксируются совместно; retry передаёт прежний ciphertext, а не повторно шифрует как новое сообщение. [S12]

Для файлов — независимый случайный ключ на blob, стандартная AEAD на ограниченные chunks, аутентифицированный manifest с порядком, полной длиной и числом chunks внутри E2E сообщения. Повтор chunk использует прежний ciphertext; изменение файла создаёт новый blob/key. Реализация обязана исключать повтор nonce под одним ключом, подмену порядка и незаметное усечение.

Для звонков — Opus + RTP/SRTP через libsrtp, без полного WebRTC network stack. Свежие направленные SRTP key/salt доставляются через установленную E2E сессию и привязываются к call_id/epoch и обоим участникам. После реконнекта создаётся новая media epoch; старый ключ не используется с обнулёнными счётчиками. Сервер пересылает ciphertext. SRTP позволяет использовать готовую replay protection; это не освобождает от корректной настройки библиотеки. [S13]

На устройстве Keystore защищает wrapping key; зашифрованные device secrets, ratchet state и локальное содержимое хранятся в app-private storage. Не обещаем, что произвольные X25519 ключи Rust автоматически находятся внутри аппаратного Keystore. История и имена файлов не выводятся в уведомления по умолчанию. [S14]

Аутентификация msgd не запрещает неизвестному участнику начать DNS/QUIC handshake. Для закрытия самого транспортного handshake нужна отдельная транспортная доработка, не скрытая задача MVP. Шифрование не скрывает tunnel domain, время и объём DNS-трафика; msgd видит маршрутизацию и состояние аккаунтов.

## 8. Протокол, очереди и доставка

Версионированные wire DTO, явные opcode, bounded length framing, postcard для небольших структур, raw bytes для media/blob payload. Совместимость фиксируется тестовыми векторами: внутренние Rust-структуры не являются wire contract.

Один Slipstream transport на устройство. Control stream долгоживущий в режиме «На связи»; отдельные streams для bulk и media открываются по необходимости. Не держим пустые media lanes постоянно. Приоритет прикладной выдачи: control и сигнализация, затем live voice, текст, voice notes, файлы. Вызов приостанавливает bulk в обоих направлениях и на сервере; уже переданные transport buffers мгновенно отменить нельзя.

Начальные ограничения: wire frame до 16 KiB, blob chunk до 8 KiB, одна активная bulk-передача, малое ограниченное окно. Длинных неограниченных очередей в RAM нет. Живой голос не попадает в persistent outbox.

Сообщения: at-least-once delivery плюс дедупликация по sender_device/message_id. Клиент показывает отдельно «в очереди», «принято сервером», «доставлено», «ошибка/истекло». Read receipts отложены. ACK серверу отправляется только после локального durable сохранения; сетевой ACK не равен пользовательскому прочтению. Контроль доставки и inbox cursor переживают рестарты. ACK группируются, сообщения после разрыва синхронизируются по cursor.

Начальные лимиты продукта:

- Текст: до 4 KiB UTF-8.
- Голосовое: до 60 секунд и 128 KiB, останавливается по первому достигнутому лимиту; Opus mono 12 kbit/s.
- Фото: после уменьшения до 1024 px по длинной стороне и до 256 KiB; metadata удаляется локально.
- Любое вложение: до 512 KiB; автозагрузка выключена.
- Серверный mailbox: до 512 событий и 32 MiB на аккаунт; TTL недоставленных данных и blobs 7 суток.
- Незавершённая загрузка: TTL 24 часа, reservation под квоту, уборка orphan chunks.

Размеры файлов задаются для итогового wire ciphertext, включая служебные данные. Сервер проверяет ciphertext bytes, права доступа, rate limits и квоты. Он не может независимо проверить продолжительность/тип E2E содержимого: клиент валидирует фактическое декодирование, размеры изображения, длительность аудио и ограничивает выделение памяти.

При 100 kbit/s полезного upload передача 512 KiB требует минимум около 42 секунд до дополнительных расходов. Скорость DNS-wire и скорость полезных данных не смешиваются. UI показывает размер и прогресс; передача возобновляется, а не начинается заново после каждого разрыва.

## 9. Звонки: эксперимент до продуктового обещания

Начальный профиль: Opus mono, 12 kbit/s с диапазоном 8–16, packet duration 40 ms, DTX, PLC, FEC только после сравнительного теста. Jitter buffer ограничен, имеет адаптацию; просроченный звук отбрасывается. Увеличение длительности codec packet не означает такое же кратное сокращение DNS queries. [S15]

Начинаем с одного media stream отдельно от control/bulk. Сравниваем 1/2/4 lanes только в эксперименте. QUIC streams независимы по порядку доставки, но разделяют congestion/connection flow control и нижележащий DNS-путь; поздние retransmissions сами не исчезают. UoT не является QUIC DATAGRAM. При общем stall все lanes могут остановиться. [S16, S17]

Проверяется весь путь телефон A → resolver → сервер → resolver → телефон B, при двух плохих uplink и одновременно говорящих участниках. Измеряются mouth-to-ear latency, доля кадров, пришедших до deadline, паузы и рост очередей, а не одна скорость download.

Кандидат критериев пилота: 20–30 минут двустороннего разговора; p95 сквозной задержки до 700 ms; не более 5% просроченных кадров; отсутствие роста задержки во времени; отдельно ограниченное количество длинных пауз и проверка понятности речи. Это требования для согласования/испытаний, не предсказанная характеристика.

При непрохождении gate сохраняем текст, voice notes и файлы, а live-call остаётся экспериментальным. PTT может улучшить разговорную очередность, но не гарантирует устранения сетевых stalls. Переход на настоящий unreliable media transport — отдельный будущий проект; существующий транспорт ради него в MVP не переписывается.

## 10. Эксплуатация, история и дальнейшее развитие

Исходники транспорта закреплены Git submodule/subtree, приложение и небольшие адаптации отслеживаются обычными коммитами. Решения, протокол и benchmark summaries лежат в Git. Нет отдельных реестров контрольных сумм для истории разработки. Подпись APK и криптографическая проверка сообщений остаются необходимыми механизмами безопасности.

CI: native tests, sanitizers, fuzz bounded parsers, Rust tests, Android release build, ABI/page-size smoke, protocol compatibility, two-client integration. Секреты, raw QNAME, содержимое и аудио не сохраняются в CI artifacts.

Резервная копия создаётся согласованно через backup API/остановку записи, вместе с immutable blobs и нужными ключами сервера; восстановление проверяется на отдельном инстансе. Копирование одного live SQLite файла без WAL не считается backup. До обновления schema делается backup; несовместимый downgrade не обещается. APK подписывается постоянным release key с отдельным защищённым хранением.

К HA заранее оставляем только разделение transport/server identity и account identity, reconnect и idempotence. Не добавляем распределённую БД, несколько серверов или фальшивую отказоустойчивость через два NS на одном VPS. Один сервер остаётся единой точкой отказа.
